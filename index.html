Why MoE Models Need Grouped Matmul

In a dense Transformer, every token multiplies against the same feed-forward weights in one uniform operation. In a Mixture-of-Experts (MoE) model, dynamic token routing creates uneven, ragged token counts per expert—breaking naive GPU/TPU execution unless fused with grouped_matmul (gmm / ragged_dot).

Dense FFN vs. Mixture-of-Experts Routing

Why moving from a dense model to a sparse MoE changes the fundamental shape of matrix multiplication on TPU Matrix Multiply Units (MXUs).

Dense Architecture · e.g., Llama 3.2 1B

Uniform Matrix Multiplication

Every token in a batch goes through the exact same Feed-Forward Network (FFN) weight matrix. That produces one large, rectangular matrix multiplication ([Tokens, Hidden] × [Hidden, Intermediate]), keeping the TPU’s 128×128 systolic MXUs continuously saturated.

Sparse MoE · e.g., Qwen 3 MoE 30B–235B, Gemma 4 MoE

Dynamic, Ragged Token Counts per Step

A learned router dynamically dispatches different numbers of tokens to different expert FFNs on every training step—for example, Expert 0 gets 510 tokens, Expert 1 gets 35 tokens, and Expert 2 gets 290 tokens. Each expert has its own distinct weight matrix W_e.

How the Three MoE Execution Approaches Compare

Why standard loop dispatch and static batch padding bottleneck MoE training, and how gmm / ragged_dot eliminates both penalties.

Naive Approach #1

For-Loop Over Experts

Iterating for e in range(num_experts) launches dozens of tiny, separate matrix multiplications back-to-back. Dispatch overhead creates gaps between launches, while lightly loaded experts (like 35 tokens on a 128-row MXU tile) starve the systolic array and tank hardware utilization.

Hardware Starved · N Separate Kernel Launches

Naive Approach #2

Padding All Experts to Max Size

Padding every expert buffer up to max_tokens = 510 allows one batched matmul [3, 510, K], but forces the TPU to read and multiply 695 fake zero rows (475 on Expert 1 + 220 on Expert 2)—wasting 45.4% of FLOPs and HBM memory bandwidth on padded zeros.

1 Launch · 45.4% Wasted FLOPs & HBM Bandwidth

The Pallas Kernel Solution

Grouped Matmul (gmm / ragged_dot)

Packs all routed tokens contiguously into one flat tensor [835, K] alongside stacked expert weights [Num_Experts, K, N] and group_sizes = [510, 35, 290]. A single fused Pallas kernel streams VMEM tiles directly into the MXU across expert boundaries with zero wasted HBM padding.

1 Fused Kernel · 0% Padding · Full MXU Saturation
